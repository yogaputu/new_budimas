## Perubahan perilaku

1. **Stok opname:** company eskalasi diambil dari principal; koreksi FISIK disimpan pada kolom canonical dan legacy secara konsisten; label dan konversi UOM mengikuti master produk. Nilai fisik/Good/Bad awal dari WMS tidak dihapus ketika detail dibuka.
2. **Company stok transfer:** company asal/tujuan pilihan form disimpan pada header dan digunakan oleh daftar, detail, filter, scope akses, armada, inventory ledger, serta jurnal. Principal produk harus milik company asal; company tujuan tetap dapat berbeda. Cabang yang digunakan beberapa perusahaan tidak lagi otomatis menentukan company transaksi. Akun legacy tanpa company eksplisit tetap dibatasi cabangnya. Transfer lama menggunakan company principal tunggal yang sesuai dengan cabang, lalu default cabang sebagai fallback; riwayat yang ambigu tidak dapat direkonstruksi pasti.
3. **Penerimaan transfer:** stok, detail penerimaan, ledger, dan jurnal memakai satu transaksi. Gagal membuat jurnal yang memiliki mapping menggulung balik perubahan. Mapping 9/10 kosong tetap mengizinkan penerimaan sesuai alur lama dan pilihan pengguna, dengan status API `not_configured`/`partially_created` serta peringatan kuning “Jurnal belum terbentuk…” setelah refresh otomatis. Kunci header dan validasi status mencegah penerimaan dua kali. Master COA/MAL tidak diubah.
4. **Promo All-In:** endpoint lokal `PATCH /api/promo/unified/<id>/status` sudah benar, tetapi endpoint dan metode `set_program_status` belum ada pada source server. Request OPTIONS publik sebelum deployment mengembalikan 404. Release menyertakan kedua file yang tertinggal. Pengujian route sebenarnya mencakup nonaktif/aktif, promo yang telah digunakan, serta ID tidak ada/deleted.
5. **Dashboard SPV:** pembacaan identitas/scope memakai koneksi baca terpisah agar tidak membuka transaksi bertingkat. Kegagalan salah satu panel tidak menghapus panel lain yang berhasil dimuat. Target MTD yang gagal ditandai tidak tersedia, bukan nominal nol. Default dan filter tanggal/bulan tidak valid diuji tanpa koneksi database aplikasi.
6. **Absensi sales:** filter UI mengirim `id_user_sales`; backend membedakannya dari ID master sales. Ringkasan dan detail memakai scope SPV/perusahaan/cabang yang sama. Sales tanpa kunjungan tetap muncul, sales lintas cabang dalam mapping SPV tidak tersembunyi oleh cabang bawaan, dan kunjungan mengikuti pemilik sales master meskipun ID user lama pada plafon tidak selaras.
7. **Order canvas web/mobile:** stok orderable dihitung terhadap approval yang dipilih, reservasi, stok fisik, dan konversi UOM yang sama dengan validasi saat simpan. Mobile dapat memilih approval terdahulu yang masih berlaku dan mengirim ID approval itu. Sisa 16 PCS pada approval yang dipilih menerima order 15 PCS dalam pengujian; jumlah fisik lintas approval tidak ditampilkan sebagai stok orderable satu approval.
8. **Piutang canvas finance:** fitur jurnal 40/41 masuk dispatcher handler generik yang sudah memiliki validasi mapping, keseimbangan, dan idempotensi. Mapping kosong/tidak valid tetap memblokir finalisasi. Audit server read-only memastikan mapping 40/41 tersedia untuk BMM dan TMP, masing-masing dengan debit/kredit lengkap.
9. **Mobile WMS retur canvas:** endpoint penerimaan sebelumnya hanya mencari KPR/retur penjualan. Sekarang kode `RT-CNV-YYYYMMDD-id`, `RT-CNV-id`, dan `CANVAS-RETUR-id` diarahkan ke sumber retur canvas yang disetujui. Scan ulang memakai antrean karantina yang sama; input qty dari klien tidak dapat menambah stok. Stok gudang berubah melalui QC sesuai alur yang sudah ada. Aplikasi WMS yang terpasang dapat memakai perbaikan API ini tanpa APK baru. Source lokal WMS yang tidak lengkap dipulihkan dari salinan server; seluruh 133 route server, perbaikan opname pagi, dan route target-racks lokal dipertahankan.

## Urutan deployment

1. Backup source API, frontend, APK alias lama, schema database, dan data tabel stock_transfer/stock_transfer_detail telah dibuat pada `/www/backup/budimas-revisi-20260629-20260928-164444`. Dump diverifikasi dengan `pg_restore --list`. Database target terkonfirmasi PostgreSQL `budimas_dev`; backup database dibatasi schema dan tabel yang terkait perubahan, bukan dump penuh database 23 GB.
2. Migration tambahan `API/tools/migrations/20260928_stock_transfer_company_scope.sql` telah dijalankan dalam transaksi dengan batas waktu lock/statement. Dua kolom nullable INTEGER dengan foreign key terverifikasi ada; transaksi lama tidak ditulis ulang. Salinan SQL yang dieksekusi tersimpan di folder release pada backup server.
3. Audit read-only memastikan prasyarat dan mapping canvas 40/41 tersedia, sehingga migration canvas dan seed akun tidak dijalankan. MAL 9/10 kosong ditangani sebagai warning sesuai pilihan pengguna; tidak dibuat mapping akun otomatis.
4. Deploy file API dalam daftar di atas sebagai satu release, termasuk helper baru; reload/restart service API sesuai konfigurasi server. Untuk 404 Promo All-In, pastikan release API menyertakan endpoint status pada `apps/routes/promo.py`, service `apps/services/UnifiedPromo.py`, dan registrasi blueprint pada `app.py`; source ketiganya sudah benar secara lokal dan tidak dipatch pada revisi ini. Periksa bahwa trafik masuk ke versi service tersebut.
5. Deploy ERP pada `/www/wwwroot/new_budimas` (443) dan `/www/wwwroot/new_budimas/dist` (9092), mempertahankan asset ber-hash lama untuk browser yang masih memakai index lama. Upload APK `/downloads/BudimasMobile-v1.0.4-debug.apk` dan perbarui alias `/downloads/BudimasMobile-debug.apk`.
6. UAT: simpan eskalasi opname dan buka ulang koreksi FISIK/UOM; transfer BMM antar cabang bersama dari create sampai receipt; uji gagal jurnal tanpa perubahan stok dan cegah penerimaan ulang; nonaktif promo yang sudah digunakan; buka dashboard tanpa filter; pilih sales lintas cabang yang diizinkan; order 15 dari sisa approval 16 PCS; buat jurnal setoran canvas lalu finalisasi tanpa jurnal ganda saat retry.
7. Jika perlu rollback, pulihkan release source/API/frontend sebelumnya. Kolom transfer tambahan dapat tetap ada karena nullable; jangan menghapus data transaksi atau jurnal sebagai cara rollback.

Source server dibandingkan dengan snapshot sebelum pemasangan; deployment berhenti jika ada perubahan bersamaan. API direload melalui `/usr/local/bin/uwsgi --reload /www/wwwroot/API/uwsgi.pid`. Script release menyediakan pemulihan source/frontend jika verifikasi API gagal. Hasil eksekusi dicatat pada `deploy-result.json` di folder backup server.
